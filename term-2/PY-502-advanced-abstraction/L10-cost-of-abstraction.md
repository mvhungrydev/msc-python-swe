# PY-502 · Lesson 10 — The Cost of Abstraction

**Estimated study time:** 3 hours
**Prerequisites:** all of PY-502

---

## 1. Orientation

This course has spent nine lessons teaching you to build machinery. This one is about not
using it.

The failure mode is specific and recognizable. A codebase where:

- a `Handler` is registered by a metaclass, configured by a decorator, whose fields are
  descriptors generated from annotations, dispatched through a plugin registry populated at
  import time;
- every one of those decisions was individually defensible;
- and a competent engineer needs two hours to answer "what happens when a request arrives".

That codebase is not the product of ignorance. It is the product of *skill without a cost
model*. This lesson supplies the cost model.

## 2. Theory

### 2.1 What abstraction costs

An abstraction is a trade: you hide detail, and you pay in these currencies.

**Indirection cost.** Every layer is a hop the reader must follow. The relevant measure is
not "how many layers" but **how many files must I open to answer a question I actually
have?** Three files to understand a request path is normal. Nine is a defect.

**Discovery cost.** Can a reader *find* the implementation? Grep for a method name finds it
if it is written literally. It finds nothing if the method is generated by `exec`, or if it
is dispatched by a string key, or if the name is assembled from parts. **Greppability is a
real and undervalued property.**

**Tooling cost.** Go-to-definition, autocomplete, type checking, refactoring tools, and
debuggers all work on code that exists statically. Everything generated at runtime is
invisible to them. This cost has risen sharply as typed Python has become the norm.

**Debugging cost.** A stack trace through five decorator wrappers, a metaclass `__call__`,
and a descriptor `__get__` tells you almost nothing about your code.

**Learning cost.** Every custom mechanism is a thing new team members must learn *before*
they can be productive, and which they cannot look up in the Python documentation.

**Wrongness cost.** The abstraction encodes assumptions. When those assumptions turn out
wrong, the cost of changing them is proportional to how many places depend on the
abstraction — which is exactly the number that made it seem worthwhile.

### 2.2 What abstraction buys

Fairly stated, because the argument is not one-sided:

- **Change amplification prevented.** One change instead of forty. This is the real one, and
  it is worth a great deal.
- **Cognitive load reduced *at the call site*.** A caller who does not need to know is
  better off not knowing.
- **Invariants enforced structurally.** A field that cannot be set wrong is better than a
  convention that it should not be.
- **Uniformity.** Fifty handlers that behave identically because they share machinery.

Ousterhout's framing is the most useful available: a good module is **deep** — a simple
interface hiding substantial implementation. A bad module is **shallow** — an interface
nearly as complex as what it hides. The question is not "is this abstract?" but
"**what is the ratio?**"

A `Repository` interface with six methods wrapping six SQL statements is shallow: the
interface is as complex as the implementation, and it adds a hop while hiding nothing. A
`ConnectionPool` with `acquire()`/`release()` hiding health checks, retry, backoff, sizing,
and eviction is deep. Same "amount" of abstraction; opposite value.

### 2.3 The rule of three, and why it is right

**Do not abstract until you have three concrete cases.**

Two cases give you no information about what varies. The abstraction you extract from two
examples encodes the accidental similarities as well as the essential ones, and you will
not know which is which until the third case arrives and does not fit.

The corollary that people miss: **duplication is cheaper than the wrong abstraction.**
Sandi Metz's formulation — "prefer duplication over the wrong abstraction" — is right
because the costs are asymmetric. Duplicated code that turns out to need to diverge is
easy: you change one copy. A wrong abstraction that needs to diverge is hard: you add a
parameter, then a flag, then a hook, then a subclass, and each addition makes the next one
harder while the abstraction drifts further from any coherent idea.

The diagnostic that a shared abstraction has gone wrong: **boolean parameters that select
behaviour.** `def process(data, *, legacy=False, strict=True, skip_validation=False)` is
three functions wearing a trench coat, and each new flag doubles the number of untested
paths.

### 2.4 Preferring the boring mechanism

For any given need, prefer the leftmost that works:

```
plain function
  → class with methods
    → composition / dependency injection by argument
      → decorator
        → descriptor
          → __init_subclass__ / class decorator
            → metaclass
              → code generation
```

Each step right buys power and costs discoverability, tooling support, and reader
familiarity. A codebase that uses only the first four is one that any competent Python
programmer can read on day one.

Concretely, for the same registration requirement (L03 §3): an explicit dict of handlers is
at position 1; a `@register("json")` decorator is at position 4; `__init_subclass__` is at
6; a metaclass at 7. All four work. The explicit dict is the one a new hire can find with
grep, understand instantly, and cannot break by forgetting an import.

### 2.5 A decision procedure

Before adding an abstraction, answer these in writing:

1. **How many concrete cases exist right now?** Fewer than three: stop.
2. **What exactly varies between them, and what is stable?** If you cannot name the axis of
   variation in one sentence, you do not understand the problem yet.
3. **What is the ratio?** Lines of interface to lines of hidden implementation. Below about
   1:5, question it.
4. **What breaks in the tooling?** Type checking, autocomplete, go-to-definition, grep. List
   the losses.
5. **How does someone find the implementation?** Trace the path a new reader takes. Count
   the files.
6. **What is the escape hatch** for the case this does not fit, and how ugly is using it?
7. **What is the cost of being wrong?** How many call sites would have to change if this
   abstraction turns out to be the wrong shape?

If you cannot answer 2 and 7, you are not ready to build it.

### 2.6 Removing abstractions

Removal is a skill, and it is rarer than it should be because deleting someone's clever
mechanism feels rude and because the abstraction is load-bearing by the time you notice it.

Signals that an abstraction should go:

- **One implementation, ever.** An interface with a single implementer is a hop with no
  polymorphism. (Exception: it exists for *testing* — but then say so, and consider whether
  a fake at a different seam would do.)
- **Every use passes the same arguments.** The parameterization is unused.
- **Flags selecting behaviour.** §2.3.
- **The abstraction leaks.** Callers must know the implementation to use it correctly
  (a "repository" whose users must know it does N+1 queries).
- **Nobody can explain it.** Ask three people what it is for; if you get three answers, it
  has no coherent purpose.
- **It is only used through a wrapper** that adapts it back to something concrete.

The technique is **inline, then re-extract**: inline the abstraction back into its call
sites (mechanical, safe with tests), observe the duplication that results, and re-extract
only if a *better* abstraction is now visible. Often nothing needs re-extracting, and the
inlined version is shorter than the abstracted one was.

### 2.7 The performance dimension

Abstraction also costs cycles, and after PY-501 L08 you can reason about it:

- Each Python-level layer is a `CALL` — cheaper since 3.11's inlined Python-to-Python calls,
  but not free.
- A descriptor access is a `__get__` call instead of a dict lookup.
- A decorator adds a wrapper frame per call.
- A `Protocol`/ABC dispatch may defeat specialization if the call site is megamorphic
  (PY-501 L08 §2.6).
- Generated code is fine at runtime but costs import time, which matters for CLIs and
  serverless cold starts.

For 99% of code this is irrelevant and optimizing it is a mistake. For the 1% in a hot loop,
the correct move is usually to *remove a layer*, not to micro-optimize inside it. Measure
first (PY-602 L01); "this is slow because of abstraction" is a hypothesis, not a finding.

## 3. Construction: an abstraction audit

Take a real codebase — yours, ideally one you did not write alone.

**Step 1 — inventory.** List every abstraction mechanism in use: base classes, Protocols,
ABCs, decorators, descriptors, `__init_subclass__`, metaclasses, code generation, registries,
plugin systems, DSLs. For each: how many implementations, how many call sites.

**Step 2 — the single-implementation list.** Every interface with exactly one implementer.
For each, ask: does it exist for testing? Would a different seam serve better? What would
inlining it look like?

**Step 3 — measure the depth ratio.** For five of the largest abstractions, count lines of
interface (signatures + docs) against lines of implementation hidden. Rank them. The shallow
ones are your candidates.

**Step 4 — the reader trace.** Pick the three questions a new team member would most likely
ask ("where does a request get authenticated?", "where is the price calculated?", "what
happens when the job fails?"). For each, count the files you must open and the
non-greppable hops (dispatch by string key, generated method, dynamic import).

**Step 5 — inline one.** Choose the worst-performing abstraction from steps 2–4. Inline it.
Measure: total lines before and after, files touched to answer step 4's questions before and
after, and whether any duplication appeared that you actually mind.

**Step 6 — write it up** as a short technical report: findings, the one change you made,
what it cost, and the two you decided *not* to make and why. That last part is the mark of
judgement rather than zeal.

## 4. Failure modes

- **Abstracting at two cases.** §2.3.
- **Boolean flags selecting behaviour.**
- **Shallow modules.** Interface as complex as the implementation.
- **Single-implementation interfaces** that exist "for flexibility".
- **Framework-building instead of problem-solving.** The clearest symptom: the machinery has
  more code than the things using it.
- **Reaching for the rightmost mechanism.** §2.4.
- **Abstractions with no escape hatch.**
- **Refusing to delete.** Sunk cost, applied to code.
- **Abstracting for a future that does not arrive.** YAGNI is right more often than not;
  the cases where it is wrong are the ones where reversing later would be expensive, and
  *that* is the criterion — reversibility, not likelihood.
- **Over-correcting into no abstraction at all.** A codebase with forty copies of the same
  retry loop has the opposite problem and it is also bad. This lesson is a corrective, not a
  doctrine.

## 5. Exercises

### Warm-up (25 min)

**W1.** Find a function in your codebase with two or more boolean behaviour flags. Split it
into separate functions. Report the change in total lines and in the number of possible code
paths.

**W2.** Find an interface with one implementation. Determine why it exists. Write one
paragraph arguing for keeping it and one for removing it, then decide.

**W3.** Compute the depth ratio for three modules. Rank them.

### Core (2 h)

**C1 — The audit.** Complete §3, all six steps, on a real codebase. Deliverable: the
inventory, the ratios, the reader traces with file counts, the one inlining with
before/after measurements, and the written report including the two changes you declined.

**C2 — Rewrite a clever thing plainly.** Take the most metaprogramming-heavy module you have
access to. Rewrite it using only the first four mechanisms of §2.4. Compare: lines of code,
what the type checker knows, grep-ability of key names, and the time for a colleague
unfamiliar with both to answer three questions about behaviour (actually time them — this is
the measurement that settles the argument).

**C3 — The three-cases rule, retrospectively.** Find an abstraction in your history that was
extracted from two cases. Trace what happened to it: how many parameters and flags did it
accumulate? Write up the history as a case study. If it turned out fine, say so and analyse
why — the rule is a heuristic, not a law.

**C4 — Cost of layers, measured.** Build the same functionality with 1, 3, and 6 layers of
indirection (function → class → decorator → descriptor → dispatch). Measure call overhead
per layer on your interpreter, and separately measure import time for the generated-code
version. Report the numbers. Then state where in a real system the overhead would and would
not matter.

### Challenge

**X1.** Read Ousterhout's *A Philosophy of Software Design*, chapters 4–10, and Metz's
"The Wrong Abstraction" (2016). Write 1,500 words applying their arguments to a real
system you know: name three deep modules and three shallow ones, with the ratio evidence,
and propose a change to one of the shallow ones. Then argue the *strongest case against*
your own proposal.

**X2.** This is your PY-502 position paper in draft form. Take the question *"when is
metaprogramming a better answer than repetition?"* and answer it with a falsifiable claim
plus evidence from your own audit. Include the case where you were wrong — where you built
something in this course that you now think should not exist. That admission, well argued,
is the highest-scoring answer available.

## 6. Self-check

1. Name the six costs of abstraction.
2. State Ousterhout's deep/shallow distinction and give one example of each from real code.
3. Why is duplication cheaper than the wrong abstraction? Why are the costs asymmetric?
4. Give the mechanism ladder from §2.4 in order.
5. What does a boolean behaviour flag indicate?
6. Give six signals that an abstraction should be removed.
7. What is "inline, then re-extract" and why in that order?
8. What is the correct criterion for YAGNI — likelihood, or something else?

## 7. Primary sources

- Ousterhout, *A Philosophy of Software Design*, 2nd ed., chs. 4–10.
- Metz, "The Wrong Abstraction" (2016). One page.
- Parnas, "On the Criteria To Be Used in Decomposing Systems into Modules" (1972) — the
  original, and still the best statement of what abstraction is *for*.
- Brooks, "No Silver Bullet" (1986) — essential vs accidental complexity; every abstraction
  you add is accidental complexity unless it removes more essential complexity than it adds.
